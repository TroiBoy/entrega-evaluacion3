# Glosario Integral de Servicios AWS, Hardware IoT, Protocolos y Conceptos del Documento Técnico — APITECH 2.0

Este glosario explica de forma clara qué hace cada servicio de **Amazon Web Services (AWS)**, cada componente de **hardware y firmware**, cada **protocolo de comunicación** y cada **entidad o indicador (KPI/SLA)** del documento técnico oficial **`Eva4ApiTechJorimCaroAndresDiaz.pdf`** aplicado en **APITECH 2.0**.

---

## 1. Servicios de Amazon Web Services (AWS) Aplicados

| Servicio / Componente AWS | ¿Qué es? | ¿Qué hace exactamente en APITECH 2.0 y dónde está aplicado? |
|---|---|---|
| **AWS IoT Core** | Broker de mensajería administrado en la nube para dispositivos IoT. | Es la **puerta de entrada principal** de toda la telemetría. Recibe los mensajes que envía la pasarela Heltec V4 mediante **MQTT 3.1.1 sobre TLS (puerto 8883)**. Verifica la identidad criptográfica de cada dispositivo y evalúa reglas SQL para enviar los datos a AWS Lambda. Endpoint verificado: `a2jvdwy68yzv30-ats.iot.us-east-1.amazonaws.com` (`aws/iot-core/`). |
| **Thing Registry (Registro de Cosas de IoT Core)** | Catálogo de identidades de dispositivos dentro de AWS IoT Core. | Registra individualmente cada equipo físico o simulado: las **4 Pasarelas** (`apitech2-gw-los-arrayanes-01`..`04`) y los **12 Nodos Heltec V4** (`apitech2-node-heltec-01`..`12`). Evita que varios dispositivos compartan una misma credencial (`aws/iot-core/thing_registry_template.json`). |
| **Certificados X.509 y Políticas de AWS IoT** | Certificados digitales criptográficos (RFC 5280) y reglas de control de acceso para dispositivos. | Autentican mutuamente a la pasarela/nodo y a AWS IoT Core sin usar contraseñas en texto plano. La política `iot_policy_per_device.json` exige que un dispositivo solo pueda conectarse con su propio `ThingName` (`${iot:Connection.Thing.ThingName}`) y publicar únicamente en `apitech/{apiario_id}/{colmena_id}/telemetria`. |
| **Reglas de AWS IoT (IoT Topic Rules)** | Motor SQL dentro de IoT Core que filtra y enruta mensajes MQTT entrantes. | La regla `apitech2_telemetry_ingest_rule` (`aws/iot-core/topic_rules.json`) escucha el filtro `apitech/+/+/telemetria`, extrae el `apiario_id` y `colmena_id` del topic, invoca automáticamente a AWS Lambda y, si ocurre un fallo de entrega, desvía el mensaje a Amazon SQS (`errorAction`). |
| **AWS Lambda** | Servicio de cómputo *serverless* (sin servidor permanente) que ejecuta código en respuesta a eventos. | En lugar de mantener un servidor encendido 24/7 esperando lecturas cada 30 minutos, Lambda se ejecuta solo cuando llega una medición. En **APITECH 2.0** se implementó en **Python 3.12** (`boto3` + `psycopg`) separado en **6 funciones independientes** (`aws/lambdas/`):<br>1. **`lambda_validator_normalizer`**: Valida el esquema JSON, el topic MQTT, el UUID y los rangos físicos.<br>2. **`lambda_telemetry_processor`**: Controla la **idempotencia** (`id_medicion` UUID), detecta reenvíos históricos atrasados (`CP09`) y guarda en PostgreSQL.<br>3. **`lambda_threshold_evaluator`**: Evalúa umbrales (`SP2.1`), abre o actualiza episodios de alerta deduplicados (`SP2.2`) y los cierra automáticamente al normalizarse la variable (`SP2.3`).<br>4. **`lambda_event_generator`**: Genera recomendaciones operativas según el periodo apícola y publica métricas en CloudWatch.<br>5. **`lambda_error_handler`**: Gestiona reintentos y envía tramas fallidas a la cola SQS Dead Letter Queue.<br>6. **`lambda_admin_catalog`**: Función administrativa (`CU09` del PDF) para mantener catálogos, instalaciones y reglas con permisos IAM. |
| **Amazon RDS for PostgreSQL** | Servicio de base de datos relacional PostgreSQL administrado por AWS. | Almacena de forma persistente, transaccional (ACID) y normalizada toda la información del sistema (16 tablas: apiarios, pasarelas, colmenas, nodos, instalaciones, sensores, telemetría histórica, reglas, alertas, recomendaciones y eventos). Configurado en instancia privada (`Single-AZ`, `db.t4g.micro` / `db.t3.micro`, 20 GiB), con conexiones cifradas SSL/TLS verificadas mediante `global-bundle.pem` y respaldos diarios automáticos con retención de 7 días. |
| **Amazon Managed Grafana** | Servicio administrado de paneles de visualización y monitoreo de series temporales. | Es la **herramienta principal de visualización técnica** definida en el PDF (reemplazando la necesidad de Amazon Timestream, que dejó de admitir nuevos clientes en junio de 2025). Consulta directamente a RDS PostgreSQL mediante la vista `vw_grafana_telemetria_colmenas` y el dashboard `aws/grafana/apitech2_grafana_dashboard.json` para graficar temperatura, humedad, peso, batería, señal LoRa y alertas con filtros por apiario, colmena y fecha. |
| **Amazon SQS (Simple Queue Service) y DLQ (Dead Letter Queue)** | Servicio de colas de mensajes administradas para desacoplar componentes y tolerar fallos. | Desacopla la recepción de telemetría del procesamiento. Si una medición falla temporalmente o llega corrupta, se encola en `apitech2-telemetry-queue` (con `VisibilityTimeout = 30s` y hasta `maxReceiveCount = 3` intentos). Si agota los intentos o tiene un error de esquema, pasa a la **Dead Letter Queue (`apitech2-telemetry-dlq`)** para que ningún evento se pierda silenciosamente (`aws/sqs/sqs_queues_config.json` y tabla `cola_mensajes_sqs`). |
| **Amazon VPC (Virtual Private Cloud), Subredes Privadas y ENI** | Red virtual aislada dentro de AWS. | Aísla los recursos de datos de APITECH 2.0. La base de datos RDS se aloja en una **subred privada sin IP pública** (`PubliclyAccessible = false`). Tanto AWS Lambda como Amazon Managed Grafana se conectan a PostgreSQL dentro de la VPC mediante **ENI (Elastic Network Interfaces)** distribuidas en dos Zonas de Disponibilidad (`us-east-1a` y `us-east-1b`, requisito técnico de Grafana documentado en la pág. 30 del PDF). |
| **Security Groups (Grupos de Seguridad)** | Cortafuegos (firewalls) virtuales a nivel de interfaz de red en AWS. | Restringen estrictamente el tráfico entre componentes (`aws/vpc/vpc_network_architecture.json`). El grupo `SG-ApiTech2-RDS` bloquea todo acceso desde Internet y solo acepta conexiones TCP al puerto `5432` provenientes de los Security Groups de Lambda (`SG-ApiTech2-Lambda`), Grafana (`SG-ApiTech2-Grafana`) y el Backend Web (`SG-ApiTech2-WebApp`). |
| **AWS IAM (Identity and Access Management) e IAM Identity Center** | Sistema de gestión de identidades, roles y permisos de AWS. | Aplica el **principio de mínimo privilegio** (`aws/iam/least_privilege_policies.json`), separando los permisos de: (1) Dispositivos IoT, (2) Funciones Lambda, (3) Almacenamiento/Secretos, (4) Backend Web y (5) Administración técnica. **IAM Identity Center (SSO)** se utiliza en el PDF (`CU01`, campo `identidad_externa` de la tabla `usuario`) para autenticar al apicultor en Amazon Managed Grafana. *(En AWS Academy Learner Lab se utiliza el rol preconfigurado `LabRole`)*. |
| **AWS Secrets Manager y VPC Interface Endpoint** | Servicio de almacenamiento cifrado y rotación de credenciales y secretos. | Resguarda las credenciales de acceso a PostgreSQL (`apitech2/production/rds-postgres`) fuera del código fuente. Las funciones Lambda consultan el secreto a través de un **Endpoint Privado de VPC (TLS 443)** usando `boto3` (`aws/lambdas/common/db_client.py`), con fallback seguro a variables de entorno cuando el laboratorio restringe el servicio. |
| **Amazon CloudWatch** | Servicio de observabilidad, logs estructurados, métricas y alarmas operativas. | Recibe los logs JSON estructurados de las 6 funciones Lambda (con ocultamiento automático de secretos), supervisa invocaciones, duración `p95` y errores, grafica métricas personalizadas en el namespace `ApiTech2/Telemetry` y dispara la alarma `ApiTech2-SQS-DLQ-MessagesVisible` si se acumulan mensajes fallidos en la DLQ (`aws/cloudwatch/dashboard_and_alarms.json`). |
| **AWS Budgets** | Herramienta de control presupuestario y alertas de facturación en AWS. | Supervisa que el gasto mensual de la infraestructura cloud no supere el presupuesto planificado en el documento técnico PDF (**\$58.356 CLP mensuales** ≈ \$60 USD), enviando alertas por correo al superar el 80% del umbral. |

## 2. Componentes de Hardware, Sensores y Firmware del Documento Técnico PDF

| Componente del PDF | ¿Qué es? | ¿Qué función cumple en la colmena y en APITECH 2.0? |
|---|---|---|
| **Heltec WiFi LoRa 32 V4 (`ESP32-S3R2`)** | Placa de desarrollo microcontrolada con procesador dual-core ESP32-S3R2 (2 MB PSRAM, 16 MB Flash), radio LoRa SX1262, Wi-Fi 2.4 GHz, BLE y cargador solar/batería integrado. | Se eligió en el PDF (págs. 5–6) para operar **tanto como Nodo en la colmena como Pasarela en la zona con Internet**. Usar la misma placa en ambos extremos estandariza el código C++ y permite comunicación redundante (LoRa + Wi-Fi). |
| **Sensirion SHT45 con membrana PTFE** | Sensor digital de temperatura y humedad relativa de alta precisión (±0,1 °C y ±1 % HR) con interfaz **I²C** (`GPIO 41/42`). | Mide el microclima interno de la colmena. La membrana **PTFE** protege el sensor contra polvo, propóleo y condensación sin impedir el paso del vapor de agua. |
| **4 Sensores de Carga de 50 kg + Combinador + HX711** | Cuatro celdas de carga en puente de Wheatstone conectadas a un convertidor analógico-digital **HX711 de 24 bits** (`GPIO 4/5`) configurado a **10 muestras por segundo (10 SPS)**. | Conforman la báscula debajo de la colmena (rango operativo de 10 a 100 kg). Permite detectar flujo de néctar durante la cosecha, consumo de reservas en invernada o pérdidas abruptas por enjambrazón/pillaje con un error relativo **≤ 5 % (`KPI 4`)**. |
| **Semtech SX1262 (Enlace LoRa 915 MHz)** | Transceptor de radiofrecuencia de largo alcance y bajo consumo integrado en la Heltec V4. | Transmite las mediciones en topología estrella punto a punto desde el nodo de la colmena (donde no hay Internet) hasta la pasarela central usando la banda libre **915 MHz** (norma chilena SUBTEL Res. 1.985), con `Spreading Factor 9 (SF9)`, ancho de banda `125 kHz` y codificación `4/5`. |
| **RSSI (`dBm`) y SNR (`dB`)** | *Received Signal Strength Indicator* (potencia de señal recibida en decibelios-milivatio) y *Signal-to-Noise Ratio* (relación señal/ruido en decibelios). | Son los metadatos de radio que la **Pasarela Heltec V4** mide al recibir cada paquete LoRa y añade al JSON antes de enviarlo a AWS IoT Core. Permiten evaluar la estabilidad del enlace (`KPI 1 ≥ 95 %`) y disparar alertas de `SENAL_DEBIL`. |
| **Panel Solar 5V 500mA + Batería Li-ion 18650 (3.000 mAh 1S)** | Subsistema energético autónomo del nodo de la colmena (`3,0 V a 4,2 V`, nominal `3,7 V`). | Alimenta al nodo en terreno. Gracias al apagado de periféricos (`GPIO 36 Vext`) y al modo **Deep Sleep** del ESP32-S3 entre capturas de 30 minutos, el nodo consume **≤ 5 mA en reposo (`KPI 2`)** y logra una autonomía **≥ 72 horas sin sol (`KPI 7`)**. |
| **Cola Persistente Acotada de la Pasarela** | Buffer circular de memoria en la pasarela Heltec V4 (capacidad de 256 mensajes). | Si se corta la conexión Wi-Fi o el acceso a Internet en el campo, la pasarela sigue recibiendo las tramas LoRa de los nodos cada 30 minutos y las guarda en su cola local. Al volver Internet, reconecta en **≤ 10 minutos (`SLA-06`)** y reenvía los mensajes acumulados a AWS IoT Core. |

## 3. Protocolos, Modelo de Datos y Conceptos Operativos del PDF

| Concepto / Entidad | Explicación Técnica y Función en APITECH 2.0 |
|---|---|
| **MQTT 3.1.1 sobre TLS con QoS 1** | Protocolo ligero de publicación/suscripción usado entre la pasarela y AWS IoT Core sobre el puerto `8883`. **QoS 1 (*At least once*)** garantiza que el broker confirme la recepción (`PUBACK`); como QoS 1 puede entregar un mensaje más de una vez si la red parpadea, APITECH 2.0 implementa idempotencia en Lambda. |
| **Topic MQTT `apitech/{apiario_id}/{colmena_id}/telemetria`** | Jerarquía de canales MQTT que identifica de forma estructurada el apiario y la colmena de origen de cada medición. |
| **Idempotencia mediante `id_medicion` (`UUID`)** | Identificador único universal generado por el nodo en el instante de la lectura (`SP1.1`) y conservado idéntico en todos los reintentos LoRa y MQTT. La Lambda #2 verifica este UUID en PostgreSQL: si ya fue insertado, ignora el duplicado sin alterar promedios ni duplicar alertas (`CP03 / CP08`). |
| **Tabla `INSTALACION` (Separación Nodo ↔ Colmena)** | Entidad clave del modelo relacional del PDF (`Anexo A.6`). Registra qué `nodo_iot` estuvo instalado en qué `colmena` desde qué fecha (`desde`) hasta qué fecha (`hasta`). Si un nodo físico se daña y se reemplaza por otro, las mediciones históricas conservan su vínculo con la instalación original sin mezclarse ni solaparse. |
| **Triple Marca Temporal (`capturada_en`, `recibida_en`, `ingresada_en`)** | Diseño del PDF (`Anexo A.7`) para trazabilidad completa: `capturada_en` es la hora del nodo (admite `NULL` si el nodo no tiene reloj sincronizado), `recibida_en` es la hora UTC asignada por la pasarela vía NTP al recibir el paquete LoRa, e `ingresada_en` es el instante en que AWS Lambda inserta el registro en PostgreSQL. |
| **Frecuencia Dual: `OPERATIVO_30M` (30 min) vs `DEMO_4S` (4 seg)** | El PDF establece una captura cada **30 minutos** para operación física en terreno (ahorro energético de batería, 48 lecturas/día). Para poder demostrar, probar y visualizar cambios en vivo sin esperar 30 minutos, APITECH 2.0 incluye además el modo de demostración cada **4 segundos**, configurable de forma independiente. |
| **Episodios de Alerta (`SP2.1`, `SP2.2`, `SP2.3`)** | En lugar de crear cientos de alertas repetidas cuando una variable supera un umbral, Lambda #3 abre **un único episodio activo por regla y colmena** (`dedup_key`), guarda la medición que inició el problema (`id_medicion_inicio`) y actualiza la última medición (`id_medicion_ultima`) e incrementa `ocurrencias`. Cuando la variable vuelve a rango normal, Lambda #3 cierra automáticamente el episodio (`estado = 'RESUELTA'`, `SP2.3`). |
| **Periodos Apícolas (`Cosecha de Miel`, `Invernada`, `Polinización`)** | Contexto productivo configurable manualmente por apiario que ajusta la interpretación de las mediciones y las recomendaciones operativas (sin emitir nunca diagnósticos biológicos definitivos). |
| **Los 7 KPIs SMART y 9 SLAs del PDF** | Métricas de calidad verificables del proyecto (págs. 37–52 del PDF):<br>- **KPI 1 / SLA-03**: Recepción LoRa exitosa **≥ 95 %**.<br>- **KPI 2**: Consumo del nodo en *Deep Sleep* **≤ 5 mA**.<br>- **KPI 3 / SLA-01**: Disponibilidad operativa del nodo y del panel **≥ 95 %** (evaluados por separado durante 30 días).<br>- **KPI 4**: Error relativo del pesaje HX711 **≤ 5 %**.<br>- **KPI 5 / SLA-02**: Cumplimiento de frecuencia cada **30 min ± 5 min ≥ 95 %**.<br>- **KPI 6 / SLA-04**: Integridad de registros válidos almacenados **≥ 98 %**.<br>- **KPI 7 / SLA-05**: Autonomía energética sólo con batería **≥ 72 horas**.<br>- **SLA-06 / Continuidad**: Reconexión automática en **≤ 10 minutos** tras recuperar red/energía, respaldos diarios de RDS con **RPO ≤ 24 horas** y **RTO ≤ 8 horas**. |
